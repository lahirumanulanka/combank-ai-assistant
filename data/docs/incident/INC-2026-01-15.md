# Duplicate and failed fund transfers in mobile app

**Incident ID:** INC-2026-01-15 · **Severity:** SEV2 · **Service:** mobile-payments · **Date:** 2026-01-15 · **Duration:** 80 minutes

## Timeline
- 12:20 - Customers report duplicate or failed transfers.
- 12:24 - Alert fires; on-call engineer acknowledges.
- 12:27 - Incident declared SEV2.
- 13:13 - Flushed the campaign cache.
- 13:13 - Reversed the duplicate debits.
- 13:40 - Incident resolved; monitoring continued for 2 hours.

## Impact
312 customers were debited twice and 1,050 transfers were wrongly rejected; all duplicates were refunded within 2 days.

## Root cause
Idempotency keys are stored in a shared Redis cluster with `maxmemory-policy allkeys-lru`. A memory spike from a promotional campaign cache caused keys to be evicted early, so retried requests were not recognised: some transfers were posted twice and others were rejected with `IDEMPOTENCY_KEY_NOT_FOUND`.

## Resolution
Flushed the campaign cache. Reversed the duplicate debits.

## Follow-up actions
1. Move idempotency keys to a dedicated Redis cluster with `noeviction` and persistence.
2. Alert when Redis starts evicting keys.
